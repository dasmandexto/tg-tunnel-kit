# Альтернативные способы для каждого элемента

Для каждого элемента ниже — варианты замены, когда и почему их выбирают,
и чем они отличаются от базового комплекта.

---

## 1. Транспорт: чем заменить собственный VPS + autossh

**Базовый вариант.** VPS с sshd + `autossh -R`.

### a) Tailscale (рекомендую как лучший компромисс)
- **Что.** Mesh-VPN на WireGuard; каждое устройство получает адрес `100.x.y.z`.
- **Плюс.** Не нужен ни проброс, ни публичный IP, ни VPS. Работает за NAT оператора.
  Доступ к телефону — просто `ssh <PHONE_LOGIN>@<tailscale-ip>` из любой сети.
- **Минус.** Зависимость от стороннего координатора (можно свой Headscale).
- **Когда.** Если цель — «зайти на свой телефон откуда угодно без возни».

### b) WireGuard «вручную»
- **Что.** Свой VPN-сервер на VPS, тоннель телефон↔VPS.
- **Плюс.** Полный контроль, никаких третьих сторон.
- **Минус.** Сложнее настройка, чем autossh; в Termux нужен root или warp-режимы.
- **Когда.** Если нельзя зависеть от чужих сервисов.

### c) Cloudflare Tunnel (`cloudflared`)
- **Что.** Исходящий туннель на инфраструктуру Cloudflare + свой домен.
- **Плюс.** Красивые имена вида `phone.example.com`, HTTPS, без открытых портов.
- **Минус.** Ориентирован на HTTP(S), для чистого SSH требует `cloudflared access`
  на клиенте; телефон должен отдавать TCP-сервис.
- **Когда.** Хочется домен и веб-удобство, SSH — вторично.

### d) ngrok / аналоги
- **Плюс.** Поднимается в одну команду, TCP-туннели поддерживаются.
- **Минус.** Бесплатный тариф меняет адреса, ограничения по времени.
- **Когда.** Быстро показать/потестировать, не для постоянного доступа.

### e) Без VPS: DDNS + проброс порта на роутере
- **Что.** A-запись домена → ваш внешний IP, роутер пробрасывает порт на телефон.
- **Плюс.** Никаких посредников.
- **Минус.** Нужен публичный IP; за CGNAT не работает; порт торчит в интернет.
- **Когда.** Есть статический/полу-статический IP и контроль роутера.

## 2. Сервер на телефоне: чем заменить `sshd` в Termux

**Базовый вариант.** `pkg install openssh` → `sshd` на порту 8022.

### a) Тот же sshd, но на другом порту
Правкой `$PREFIX/etc/ssh/sshd_config` (`Port 9022`) — если 8022 занят или хочется
спрятать от типовых сканов.

### b) Отдельное SSH-приложение (SimpleSSHD и подобные)
- **Плюс.** Не требует Termux, умеет работать без постоянно висящего процесса.
- **Минус.** Меньше контроля, обычно только `scp/sftp`.
- **Когда.** Нужен просто доступ к файлам, а не полноценный shell.

### c) Dropbear вместо OpenSSH
- **Плюс.** Компактнее, иногда быстрее стартует.
- **Минус.** Урезанный набор опций, нестандартные пути.
- **Когда.** Ограничены ресурсы или нужна минимальная сборка.

### d) Не SSH, а Syncthing / WebDAV
- **Что.** Синхронизация файлов P2P (Syncthing) или файловый сервер (WebDAV).
- **Плюс.** Не даёт shell — только файлы; безопаснее по определению.
- **Когда.** Реальная задача была «доступ к файлам», а не «командная строка».

## 3. Супервизор: чем заменить `termux-services`

**Базовый вариант.** `$PREFIX/var/service/autossh/run` + `sv-enable`.

### a) `crontab` с проверкой `@reboot`
```
@reboot pgrep autossh || autossh -M 0 -N vps-tunnel -R 2222:localhost:8022
```
- **Плюс.** Просто, без установки доп. пакетов.
- **Минус.** Cron в Termux будит ОС только при живом Termux; ненадёжен после сна.
- **Когда.** Как быстрый резервный механизм.

### b) `tmux` / `screen`
```bash
tmux new -s tun -d 'autossh -M 0 -N vps-tunnel -R 2222:localhost:8022'
```
- **Плюс.** Видно, что происходит; легко подключиться и посмотреть логи.
- **Минус.** Не переживает жёсткое убийство Termux так надёжно, как сервис.
- **Когда.** Отладка туннеля.

### c) `Termux:Boot` + скрипт
- **Что.** Плагин, запускающий `~/.termux/boot/*.sh` при старте телефона.
- **Плюс.** Туннель поднимается автоматически после перезагрузки устройства.
- **Минус.** Требует установки отдельного приложения Termux:Boot.
- **Когда.** Нужен «поставил и забыл».

### d) `nohup` вручную
```bash
nohup autossh -M 0 -N vps-tunnel -R 2222:localhost:8022 >~/autossh.log 2>&1 &
```
- **Когда.** Разовый запуск для теста, без автозапуска.

## 4. Режим порта: варианты `GatewayPorts`

| Вариант | Настройка | Доступ снаружи | Безопасность |
|---|---|---|---|
| Только VPS (базовый) | `GatewayPorts no` | нет | высокая: вход через `ssh -L` |
| Клиент решает | `clientspecified` + `-R 0.0.0.0:2222:...` | да, порт на всех интерфейсах | средняя |
| Всегда наружу | `yes` | да | ниже: полагаетесь только на пароль/ключ телефона |

**Замена «входа снаружи»:** обратный прокси на VPS (nginx `stream`) перед портом 2222,
с ограничением по IP и fail2ban. Даёт фильтрацию без отказа от прямого доступа.

## 5. Аутентификация: варианты вместо «простого ключа»

**Базовый вариант.** Ключ ed25519 без пароля, `restrict,permitlisten`.

### a) Ключ с парольной фразой + `ssh-agent`
- **Плюс.** Даже при краже файла ключа он бесполезен.
- **Минус.** В Termux агент менее удобен.
- **Когда.** Если файл ключа лежит на устройстве с риском компрометации.

### b) Отдельный ключ под каждый телефон
- **Плюс.** Отзыв одного устройства не задевает остальные.
- **Когда.** Несколько телефонов на одном VPS.

### c) `Match User tunnel` с дополнительными ограничениями
```
Match User tunnel
    AllowTcpForwarding remote
    PermitOpen none
    ForceCommand /bin/false
```
- **Плюс.** Централизованно в sshd_config, а не в строке ключа.
- **Когда.** Хочется держать политику на сервере.

## 6. Клиент: чем заходить на телефон

| Способ | Команда | Особенность |
|---|---|---|
| Прямо | `ssh -p 2222 login@vps` | нужен `GatewayPorts clientspecified` |
| Jump-host | `ssh -L 8022:localhost:2222 tunnel@vps` + `ssh -p 8022 login@localhost` | порт не торчит наружу |
| Через `ProxyJump` | `ssh -J tunnel@vps -p 8022 login@localhost` | одним вызовом, то же преимущество |
| Через Tailscale | `ssh login@100.x.y.z` | вообще без VPS |
| Через SFTP | `sftp -P 2222 login@vps` | только файлы |
| Через `mosh` | требует UDP | устойчивее к смене сети, но UDP через `-R` не пробрасывается напрямую |

## 7. Вместо телефона как сервера: pull-модель

**Альтернатива всей схеме.** Не телефон слушает, а вы **забираете** данные:

- телефон по расписанию отправляет нужное на VPS (`scp`/`rsync`/`curl` по cron);
- вы читаете то, что пришло.

**Плюс.** На телефоне нет открытого порта вообще — минимизирован радиус поражения.
**Минус.** Нет интерактивного shell; только заранее заданные выгрузки.
**Когда.** Нужны бэкапы/логи, а не живая консоль. Для интерактивности — Tailscale.
