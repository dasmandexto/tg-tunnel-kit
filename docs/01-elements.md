# Разбор каждого элемента

Ниже — по одной записи на каждый элемент комплекта: **что это**, **зачем**,
**что сломается без него**, **как проверить**. Порядок — сверху вниз по потоку данных.

---

## 1. `sshd` в Termux

**Что.** SSH-сервер, работающий внутри приложения Termux на телефоне.

**Зачем.** Принимает подключения к телефону. Без него пробрасывать нечего.

**Особенность.** Слушает порт **8022**, а не 22. Приложение — непривилегированный
процесс и не может занять порт <1024. Это не ошибка, так задумано.

**Проверка.**
```bash
sshd
ss -tnlp | grep 8022
```
Ожидаемо: строка со `LISTEN` и `8022`.

**Логин.** Не `root` и не `termux`, а имя пользователя приложения:
```bash
whoami        # например u0_a123
```

## 2. `passwd` / ключ доступа

**Что.** Способ аутентификации: пароль (`passwd`) или публичный ключ (`authorized_keys`).

**Зачем.** Без аутентификации sshd никого не пустит.

**Почему в комплекте — ключ.** Пароль на публичном порту подбирается сканерами за
секунды. Ключ подобрать нельзя.

**Проверка.**
```bash
ls -l ~/.ssh/authorized_keys     # должен существовать, права 600
```

---

## 3. `~/.ssh/config` (на телефоне)

**Что.** Файл-ярлык, описывающий подключение к VPS именем `vps-tunnel`.

**Зачем.** Чтобы не писать `autossh -M 0 -N ... -R ... user@host -p 22 -i ...`;
достаточно `autossh -N vps-tunnel -R ...`.

**Ключевые строки.**
| Строка | Смысл |
|---|---|
| `ServerAliveInterval 30` | раз в 30 с шлём keep-alive, иначе NAT/оператор рвут «молчащее» соединение |
| `ServerAliveCountMax 3` | три пропуска пинга → соединение считается мёртвым, autossh переподключится |
| `ExitOnForwardFailure yes` | если проброс порта не удался — выйти с ошибкой, а не висеть «живым» без туннеля |
| `IdentityFile` | какой ключ использовать |

**Что сломается без него.** Соединение будет отваливаться при смене сети/сна, а
autossh может считать себя живым, хотя проброс не поднялся.

**Проверка.**
```bash
ssh -G vps-tunnel | grep -E "hostname|user|port"
```

## 4. `autossh`

**Что.** Обёртка над `ssh`, которая следит за соединением и перезапускает его при обрыве.

**Зачем.** Голый `ssh -R` умрёт при первом разрыве сети и сам не поднимется.

**Флаги в комплекте.**
| Флаг | Смысл |
|---|---|
| `-M 0` | отключить отдельный порт мониторинга; следим через keep-alive самого ssh |
| `-N` | не открывать интерактивную сессию — только проброс |
| `-R 2222:localhost:8022` | обратный проброс: открыть порт 2222 **на VPS**, ведущий к 8022 **на телефоне** |

**Переменные окружения.**
| Переменная | Смысл |
|---|---|
| `AUTOSSH_GATETIME=0` | **обязательно в Termux**: иначе autossh считает быстрый старт ошибкой и сдаётся |
| `AUTOSSH_POLL=30` | период проверки, секунды |

**Проверка.**
```bash
pgrep -a autossh
```

## 5. `termux-services` и скрипт `run`

**Что.** Аналог systemd в Termux: держит сервисы запущенными, поднимает после перезапуска.

**Зачем.** `systemctl` в Termux нет. Без супервизора туннель придётся поднимать руками
после каждого перезапуска приложения.

**Как устроено.** Файл `$PREFIX/var/service/autossh/run` — исполняемый скрипт; команда
`sv-enable autossh` регистрирует его как сервис.

**Проверка.**
```bash
sv status autossh
```

---

## 6. `termux-wake-lock`

**Что.** Запрос wake-lock у Android: не даёт системе усыпить процесс Termux.

**Зачем.** Без него Android через несколько минут сна убивает sshd и туннель.

**Проверка.**
```bash
termux-wake-lock        # выполнить; в шторке появится уведомление Termux
```

**Дополнительно.** В настройках Android: **Приложения → Termux → Батарея →
«Без ограничений»**. Это вторая половина того же требования, одной команды мало.

## 7. `AllowTcpForwarding` в sshd на VPS

**Что.** Разрешение на проброс портов в SSH.

**Зачем.** Без `yes` сервер отклонит запрос `-R`, и туннель не поднимется.

**Где.** `/etc/ssh/sshd_config` или `/etc/ssh/sshd_config.d/10-tunnel.conf`.

**Проверка.**
```bash
sshd -T | grep -i allowtcpforwarding
```

---

## 8. `GatewayPorts` в sshd на VPS

**Что.** Определяет, на каких интерфейсах VPS будет слушать проброшенный порт.

| Значение | Поведение | Когда выбирать |
|---|---|---|
| `no` (по умолчанию) | порт только на `127.0.0.1` VPS | **безопаснее**: вход либо с VPS, либо через `ssh -L` |
| `clientspecified` | клиент сам решает; с `-R 0.0.0.0:2222:...` порт на всех интерфейсах | если нужно подключаться напрямую `ssh -p 2222 host` |
| `yes` | всегда на всех интерфейсах | старое поведение, избыточно при `clientspecified` |

**Рекомендация комплекта.** `clientspecified` + вход через `-L` (jump-host), чтобы
порт телефона не торчал в интернет напрямую.

**Проверка.**
```bash
sshd -T | grep -i gatewayports
```

## 9. Пользователь `TUNNEL_USER` с `nologin`

**Что.** Служебная учётка на VPS, единственная задача которой — принимать туннель.

**Зачем.** Если туннель заведён под вашим основным пользователем, то утечка ключа
с телефона даёт вход на VPS. Отдельная учётка с `nologin` ограничивает ущерб.

**Проверка.**
```bash
getent passwd tunnel          # шелл должен быть /usr/sbin/nologin
```

## 10. Ограничение ключа `restrict,permitlisten`

**Что.** Префикс в начале строки `authorized_keys`, ограничивающий, что ключ может.

```
restrict,port-forwarding,permitlisten="2222" ssh-ed25519 AAAA... device-tunnel
```

| Директива | Смысл |
|---|---|
| `restrict` | отключить всё по умолчанию (shell, agent, X11, pty, ...) |
| `port-forwarding` | точечно разрешить проброс портов |
| `permitlisten="2222"` | разрешить слушать **только** порт 2222 |

**Зачем.** Даже если ключ утечёт, он не даст shell на VPS и не позволит открыть
произвольные порты — только один телефонный.

**Проверка.** После подключения с телефона shell на VPS не должен открываться:
```bash
ssh -N vps-tunnel          # просто висит, shell нет — так и надо
```

## 11. Порт `2222` и фаервол

**Что.** Порт на VPS, через который вы попадаете на телефон.

**Зачем.** Развести с 22 (SSH самого VPS) и с 8022 (порт телефона).

**Проверка.**
```bash
sudo ss -tnlp | grep 2222
sudo ufw status | grep 2222
```

## 12. Вход через jump-host (`ssh -L`)

**Что.** Способ попасть на телефон, не публикуя порт 2222 наружу.

```bash
ssh -L 8022:localhost:2222 tunnel@<VPS_HOST>      # окно держится
# в другом терминале:
ssh -p 8022 <PHONE_LOGIN>@localhost
```

**Зачем.** Порт телефона вообще не слушает внешние интерфейсы — доступ только
через уже аутентифицированную SSH-сессию на VPS.

**Проверка.** `ssh -p 2222 <PHONE_LOGIN>@<VPS_HOST>` снаружи должен **не** отвечать,
если `GatewayPorts no`.
